# Resolving a ticket's campaign/bonus identity

A ticket's "Betler campaign name/Bonus name" field is free text typed by a CS agent — sometimes an exact internal campaign name, sometimes a public/marketing name, sometimes just a vague category ("KYC offer", "casino app offer"), sometimes a promo code, sometimes an XP/comms flow name. None of these are directly look-up-able as a `campaign_id` in Betler's Kafka/OpenSearch tools — and those tools **redact the `name` field as PII** on `campaign_definitions` and on `customer_campaign_status.campaign.name`, so you can't search Betler by name even if you have the exact internal string. You need the real UUID first.

## Fast paths to a campaign_id, in order of preference

1. **The player's own `customer_campaign_status` history, if you already suspect the ID.** If a campaign_id has come up earlier in the same investigation (or session) for a similar ticket, check it directly rather than re-deriving. Campaign IDs recur constantly across tickets for recurring campaigns — don't re-search from scratch every time for an already-known pattern (see `known-bugs-and-patterns.md`).

2. **Snowflake `PROD.DWH.D_CAMPAIGN`, if you have a name fragment.** This table is NOT PII-redacted and is searchable directly by name:
   ```sql
   SELECT CAMPAIGN_ID, CAMPAIGN_NAME, CAMPAIGN_STATUS, CAMPAIGN_PERIOD, CAMPAIGN_MODE, IS_MISSION,
          MINIMUM_DEPOSIT_AMOUNT, MINIMUM_DEPOSIT_COUNT, MINIMUM_GAMING_STAKE_AMOUNT, MINIMUM_GAMING_SPIN_COUNT,
          MINIMUM_SPORTS_STAKE_AMOUNT, MINIMUM_SPORTS_TICKET_COUNT, CAMPAIGN_QUALIFICATION_CONDITION,
          CAMPAIGN_START_DT, CAMPAIGN_FINISH_DT, IS_VALID
   FROM PROD.DWH.D_CAMPAIGN
   WHERE IS_VALID = 1 AND CAMPAIGN_NAME ILIKE '%<fragment>%'
   ```
   Also returns the qualification thresholds and `CAMPAIGN_QUALIFICATION_CONDITION` (same erlang-style syntax as Betler's own `qualification.*.erlang_expression`, confirmed identical on multiple cross-checks) in one call — this is usually faster than several rounds of Notion search. `D_CAMPAIGN` is SCD2: always filter `IS_VALID = 1`, and still expect test-account rows ("Test acc_...", "test-...") and old deleted/ended/draft rows sharing the name fragment — filter to `CAMPAIGN_STATUS = 'running'` and exclude obvious test prefixes when disambiguating. `CAMPAIGN_QUALIFICATION_CONDITION` only holds one vertical's expression (gaming or sports, whichever is primary) — if you need to confirm an inactive leg is genuinely `"true"` vs. partially configured, cross-check the live Kafka `campaign_definitions` record too.

3. **Notion, if you have a promo code, an XP flow name, or a mission's public offer text:**
   - **Promo code** (e.g. "SUPER300" entered at registration or in-app): search the promo-code Notion database by the code string first — it returns the campaign/bonus identity, avoiding the mistake of confusing a code-triggered bonus with an unrelated deposit-triggered offer that happens to also apply to new players.
   - **XP/comms flow name** (e.g. "[SB] 2nd Dep Flow D8", "[CA] 2nd Dep Flow D8") — this is an XtremePush flow name, not a Betler campaign name. Search the **"XP flows + Betler campaigns connected to flows"** Notion database specifically (not the CRM OPS calendar/content-planning databases, which can have duplicate-titled rows pointing to *different* campaigns — e.g. one row mapping the same flow name to a casino FS campaign, another to the correct sportsbook Welcome Offer). The right database's rows have `Betler campaign ID`, `Betler campaign name`, `Status`, `Type of flow`. If duplicates exist even there, sanity-check the mapped campaign's domain (sport vs. casino) against the ticket's product before trusting it.
   - **A mission's public offer text or reward amount** (e.g. "Place 10 bets of €5 each → 600 Supercoins"), when you don't have a campaign_id and the Zendesk Topic field is misleading (missions sometimes get filed under an unrelated topic like "Serial Winner::Bonus Not Granted"): `lookup bonus_definitions` by any candidate bonus_id surfacing in the player's own `customer_campaign_status` records — even ones that don't look obviously related — and read `public_names`/`offer_details` (never redacted, unlike `name`) until the text matches the ticket.

4. **Betler's own `publicCampaignName` field**, if the ticket's text matches a specific public-facing name — this field isn't redacted the way `name` is, so an exact-text match against it can confirm a campaign_id you already have a candidate for.

## Resolve every unrecognized ID — don't stop at the ones you recognize

Many campaigns (KYC verification bonuses, one-time promo drops) are `fixedCampaign: "dynamic"` / `period: "one_time"` — they get a **brand-new campaign_id every time they're regenerated**. There is no single stable ID to memorize. When pulling a player's full `customer_campaign_status`/`qualified_campaigns` list, resolve (`lookup`) every ID you don't already recognize before concluding "no campaign of type X exists" — the unfamiliar ID is exactly where a newer instance of a familiar campaign type is most likely hiding. Pattern-matching against previously-seen IDs only works for genuinely stable, recurring campaigns (daily missions, etc.); it silently fails for anything regenerated per-instance.

## Only the live config governs real players

A compacted Kafka topic (`campaign_definitions`, `bonus_definitions`) keeps every historical revision, including abandoned drafts edited before ever going live. Only `lookup`'s `latest` value (or a manually-scanned revision with `status: running` / `locked: true`) ever governed a real player outcome — a draft revision, however different, was never live and explains nothing about an actual payout. Cross-check the live config's numbers against the campaign's **public T&C page** (fetch it) as the authoritative statement of what was actually promised — do this early in the investigation, not as a late correction, since a T&C page is also the fastest way to catch a wrong date window (see below).

## Category labels that aren't literal campaign names

Some ticket categories are shorthand for a specific, non-obvious campaign family — searching for the literal words will send you down the wrong path:

- **"KYC offer" / "KYC Verification Offer"** → the **"KYC & GET Promo"** family (Betler public name "Bonus Ταυτοποίησης": 200 FS + 50 FC + 750 Supercoins, same-day-triggered off `account_verified_date_ts`). This is a **different** campaign from "Register and Get" (Bonus Εγγραφής — the registration/email-verification bonus: €5 FB + 50 FS + 50 FC, 3-day expiry). Search Snowflake for `KYC & GET` specifically, not "Register and Get" and not bare "KYC" (which also surfaces unrelated country-specific KYC-lifecycle campaigns). Because it's dynamic/same-day-triggered, a player verified before a given generation existed can never retroactively qualify through the normal flow — check every generation's live window against the player's actual `account_verified_date_ts` (in `customer_attributes`, don't ask the CS agent for it, you can see it directly) before concluding either a timing gap or a genuine missed auto-qualification.
- **"Phone verification" / "20 FS phone verification"** → a standalone campaign (Le Vampire, Hacksaw, €0.20/spin ×20) that doesn't live in the normal `campaign_definitions`/Snowflake lookup paths as of its launch — it may simply not be queryable via the usual tools. **The award is not real-time — allow up to 24h after the verification event** before treating a same-day "missing" ticket as a real miss.
- **"Basketaki" / Basketaki MVP** → a real-world amateur basketball league sponsorship (basketaki.gr), **not** a Betler campaign and **not** Hunch/F2P. Don't search Betler for it, don't tag hunch-team by analogy to Serial Winner/Super Streak. Ask the CS agent for the name/email the player registered with Basketaki and have that checked against the actual MVP list (owned by marketing/sponsorship, a different team from both Betler and Hunch).
- **"Casino app offer" / "Sportsbook app offer"** → a self-serve opt-in acquisition campaign (e.g. Casino App Bet10Get50FS/Slotomoji) — the player must click "Activate Offer" in-app themselves; it cannot be manually activated from Betler. If a player genuinely can't see the offer despite looking, that's an app-display/eligibility issue for Product Support, not something Betler data explains directly. **Multiple same-day tickets with this exact shape (claims wagering happened, zero or only just-created eligibility record) is a confirmed recurring targeting/lag issue** — treat a third occurrence as a confirmed pattern worth flagging, not three coincidences.
- **"[SB] Survey | €5 Free Bet..."** or similar survey/comms campaigns marked **"Intention: Comms Only"** in the Notion CRM OPS calendar → **not an automated Betler campaign at all.** No campaign_id, no `customer_campaign_status`, no `bondet_state` record will ever exist for it, regardless of whether the player completed the survey. These campaigns' crediting (and the full responder list) typically arrives from an external provider on a fixed later date — confirm the actual timeline with the campaign owner rather than investigating Betler, which has nothing to show. A survey tool blocking re-entry after a partial submission with an "already completed" message is normal tool behavior, not a bug.
- **Super Predictor / Serial Winner / Super Wheel / Super Streak** → see the F2P/Hunch boundary section in `known-bugs-and-patterns.md` — qualifying in Betler for one of these grants *eligibility to play* an external F2P game, not an automatic bonus.
