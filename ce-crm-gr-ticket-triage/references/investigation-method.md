# Querying Betler without getting a false negative

The tools available (`opensearch_search`, `lookup`, `messages`/`messages_scan`, `partition`) all work, but several have sharp edges that produce a clean-looking, confident "zero records" or "no match" result that is simply wrong. Every one of these has been caught live, more than once, after the wrong answer had already gone into a draft reply. Treat a "nothing found" result as provisional until you've ruled these out.

## Use `opensearch_search`, not the keyed-lookup tools, for "does this exist"

`messages(topic=..., kafka_key=...)` and `check_topic_message(topic=..., kafka_key=...)` have both, independently, returned `count: 0` for a key that genuinely had real records — confirmed on two different tools, two different topics (`customer_events` and `bondet_state`/`fsinfo_state`), each time verified by finding the real data immediately via a direct `opensearch_search`. No error, no truncation warning — it just silently misses.

**Default to `opensearch_search`** for "does this player have any record of X": `index` = the topic name directly (e.g. `"bondet_state"`, `"customer_campaign_status-*"`), query `{"term": {"customer_id.keyword": "<id>"}}`. Note the `.keyword` suffix — `customer_id` and similar ID fields are mapped as analyzed `text` with a `.keyword` subfield for exact matches; a bare `{"term": {"customer_id": ...}}` against the analyzed field can silently return zero hits even though the field mapping looks right. Check `opensearch_mappings` on an index if a term query comes back suspiciously empty.

`customer_events` specifically is keyed by the **event's own ID**, not `customer_id` — `customer_id` only appears inside the message value, so a keyed lookup on `customer_id` for this topic will always return nothing regardless of real activity. To find a specific bet/spin/deposit event: get the partition (`partition(topic="customer_events", key="<customer_id>")`), then `messages_scan(topic="customer_events", grep="<customer_id>", partition=<n>, from_ms=..., to_ms=...)` — this greps the raw JSON value so it matches regardless of the real key. `messages_scan` is capped at a 1-hour window server-side; narrow the window using other signals first (a campaign status doc's `updated_at`/`opt_in_out_date`) rather than brute-forcing a whole day hour-by-hour.

## Don't let `size < total` hide the one record that matters

`opensearch_search`'s `total` field is the real match count; `size` only caps what's *returned*. Default ordering is not chronological and not guaranteed stable across a filtered query — a `size: 30` fetch against `total: 57` can drop exactly the one record you needed, and the response looks identical to genuine absence (a clean list of N non-matching records). Before concluding "no record for X," check whether `total` exceeds what you actually inspected. If it does, either narrow the filter (a tighter date range bracketing a date the human gave you) until `total <= size`, or paginate until every hit is seen. A specific date a human cites ("I see it in backoffice on the 20th") is a strong hint to re-run narrowly around that date rather than trusting a broad unscoped result.

## Betler's day boundary is ~21:00 UTC, not midnight UTC

Daily/timed campaign instances roll over around **21:00 UTC** (aligned to Greek local midnight, UTC+3), not calendar-day UTC midnight. A query filtered to `>= <today>T00:00:00Z` can silently exclude activity from late the previous UTC day that is actually part of "today's" round from the player's (and campaign's) point of view. If a first pass returns zero records for both `customer_campaign_status` and `bondet_state` right after local midnight, that's a strong signal to re-check the date window — widen to `>= <yesterday>T21:00:00Z` — before concluding nothing exists. A false "zero records" here can flip the whole recommendation (award vs. no-award).

For a campaign name containing a date suffix (e.g. "...Churn15_SBlow_28.09"), don't assume that date bounds the search window — it's very often the campaign's *creation* date or a recurring cycle's *start*, not a short one-off window. Fetch the public T&C page early (not as a late correction) for the real date range — it's the fastest authoritative source and catches this mistake immediately.

## Dig all the way through before saying "inconclusive"

Before writing "inconclusive" or "needs a follow-up," ask: is there a tool call you haven't made that would actually resolve this? A `messages_scan` window not yet scanned, a `lookup` not yet done, a specific bet ID not yet traced — make it. Only genuinely conclude "no record exists" after: fetching the T&C, resolving every unrecognized campaign_id (see `campaign-resolution.md`), and searching the player's full history (not just the window implied by a name's date suffix). Say plainly which case applies — "I couldn't finish checking" (go back and finish) vs. "the data doesn't exist to check against" (a real dead end) — never conflate the two.

## Tracing a specific bet's eligibility

When a player disputes whether a specific bet counted toward a bonus/mission:

- **A bet funded (even partly) by a different bonus is often correctly excluded.** Pull the transaction from `transactions_with_country-<date>` (query `metadata.ticket_code.keyword` — narrow to the specific day(s); the unscoped wildcard across all dates can time out) and check `funding_type`/`cash_stake_percent` and the `reserve_request` transaction's `balances_not_eligible` map. A bet with `funding_type: "mixed"` or `"bonus"`, or carrying a `bonus_info` entry for a different bonus template, didn't use the bonus in question — that's a real, verifiable reason, not a guess.
- **`bonus_definitions._excluded.market_id` alone is not proof of a real restriction.** The same ~69-entry market-exclusion list recurs verbatim across unrelated bonus templates — strong evidence it's boilerplate copied at template creation, not necessarily enforced for every bonus type. It genuinely *is* enforced for at least some mechanics (confirmed for a `Wagering`/`cash_first` bonus via the transaction-level check above). Don't flag a T&C/comms gap off the static list alone — pull the actual transaction (as above) and let its `balances_not_eligible`/`funding_type` fields be the authoritative answer; only cite the static list afterward as the likely *reason* once the transaction confirms exclusion actually happened.
- **`has_line`-style multi-leg qualification checks ANY single leg**, not every leg. A rule like `has_line({event,[...]}, [MarketId], all, Attr)` qualifies if at least one leg in the ticket's `lines[]` array matches both the event whitelist AND the market whitelist together — `all` means "both conditions on the same leg," not "every leg must pass." Never conclude "doesn't qualify" from an aggregate or first-leg read on an accumulator; enumerate every leg from `customer_events`.
- **`ticket_type` and raw `number_of_selections`/event-id count do not tell you whether a leg is a Bet Builder.** Bet Builder tickets show as `ticket_type: "single"` in transaction data (all legs grouped into one line) — this field can never rule a Bet Builder in or out. The authoritative signal is `metadata.market_id`: Betler names Bet Builder markets `"Bet Builder (<market_id>)"` in the campaign's own qualification config. A market_id that isn't the whitelisted one (e.g. a price-boosted combo bet, a different product entirely) is often a *correctly excluded, different product* — don't assume it's a missing whitelist variant without confirmation from someone with trading/backoffice knowledge.
- **A cumulative stake/bet-count requirement is not a per-bet requirement.** If a campaign's qualification has a separate `minSumBets`/`minSumBetsOnCampaignEnd` (or the sports/gaming equivalent) scoped apart from a per-bet odds/selection check, it's almost certainly summed across every qualifying bet in the window, not required in one single bet. Pull the player's `qualification_progress.currency_amount_of_bets_made` (total, settled+unsettled) vs. `currency_amount_of_settled_bets_made` (settled only) — a gap between these two, especially right at a window-close timestamp, is the settlement-timing tell (see `known-bugs-and-patterns.md`).
